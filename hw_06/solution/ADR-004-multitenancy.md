# ADR-004. Общий кластер с двухуровневым шардированием по app_id вместо изоляции по клиенту

| | |
|---|---|
| **Статус** | Принято |
| **Дата** | 2026-09-21 |
| **Контекст решения** | Раздел 4 «Хранение данных», раздел 3 «Сайзинг» |
| **Влияет на** | стоимость инфраструктуры, латентность запросов крупных клиентов, модель безопасности |

## Контекст

Платформа обслуживает **2 000 приложений-клиентов**, и распределение нагрузки между
ними крайне неравномерно: **топ-10 приложений дают около 30% всего потока**
(до 90 млн событий в сутки на одно приложение), тогда как медианное приложение —
менее 100 тыс. событий в сутки.

Это классический конфликт мультитенантности:

- схема «одна база на клиента» даёт идеальную изоляцию, но 2 000 кластеров
  ClickHouse не эксплуатируются в принципе, а медианный клиент не окупит даже одну ноду;
- схема «всё в одной таблице с шардированием по `app_id`» даёт максимальную
  утилизацию, но крупный клиент становится горячей точкой: его данные целиком
  лежат на одном шарде.

Продуктовое ограничение, которое делает задачу решаемой: **межприложенческих
запросов в продукте нет**. Каждый клиент видит только свои данные, и любой
аналитический запрос всегда содержит `app_id`.

## Решение

Один общий кластер ClickHouse, шардирование по `app_id` через **1 024 логических бакета**,
с **двумя классами маршрутизации**:

| Класс | Условие | Ключ распределения | Профиль запроса |
|---|---|---|---|
| **SMALL** | < 20 млн событий/сут (99,5% приложений) | `crc32(app_id) % 1024` → бакет → шард | все данные в одном шарде, запрос локальный |
| **LARGE** | ≥ 20 млн событий/сут (топ-10) | `crc32(app_id, device_id) % N_шардов` | данные размазаны по всем шардам, запрос scatter-gather на 96 ядер |

**Откуда взялся порог 20 млн событий в сутки.** Его задаёт не объём диска, а бюджет
латентности тяжёлого запроса. Узел ClickHouse (16 vCPU) сканирует при воронке
или ретеншн-анализе порядка **50 млн строк/с** — это агрегация с `uniq` поверх
распакованных колонок, а не простой `count`. НФТ отводит на такой запрос `p95 ≤ 10 с`,
то есть **500 млн строк** на один шард:

```
20 млн событий/сут × 30 дней = 600 млн строк  →  600 / 50 = 12 с на одном шарде ✗
то же самое на 6 шардах (96 ядер)             →  600 / 300 = 2 с              ✓
```

Диск при этом не является ограничением и близко: самое крупное приложение
(90 млн событий/сут) занимает `90e6 × 30 × 30 Б = 81 ГБ` за 30 дней при 754 ГБ
данных на узел. Именно поэтому решение — не «дать крупному клиенту больше места»,
а «дать его запросу больше ядер».

Класс хранится в Control Plane, карта бакетов — в ClickHouse Keeper с кэшем в Redis.
Перевод приложения из SMALL в LARGE — фоновая перезаливка из архива сырых событий
в теневые партиции с атомарной подменой.

Изоляция между клиентами обеспечивается **не физически, а на трёх уровнях контроля**:

1. `app_id` подставляется Query API **из JWT**, а не из тела запроса — клиент
   не может его подделать;
2. квоты и rate limit в Redis на уровне приёма — по `app_id` и по `(app_id, install_id)`;
3. лимиты ресурсов ClickHouse (`max_memory_usage`, `max_execution_time`,
   `max_threads`) в отдельном профиле на каждый класс тарифа — «шумный сосед»
   не может съесть кластер тяжёлым запросом.

## Рассмотренные альтернативы

| Вариант | Почему отклонён |
|---|---|
| **База данных на клиента** | Полная изоляция и простая модель безопасности. Отклонено по стоимости: минимальный отказоустойчивый кластер — 2 узла, то есть 4 000 узлов на 2 000 клиентов против текущих 12. Утилизация медианного клиента — доли процента. |
| **Только `crc32(app_id) % 1024`, без класса LARGE** | Проще на порядок. Отклонено арифметикой выше: воронка крупнейшего клиента за 30 дней — 2,7 млрд строк, что на одном шарде даёт около 54 с вместо заявленных в НФТ 10 с. Клиент, приносящий больше всех денег, получил бы самые медленные отчёты. |
| **Только `crc32(app_id, device_id)` для всех** | Идеальная равномерность. Отклонено, потому что превращает **каждый** запрос в scatter-gather по всем шардам. Для 99,5% приложений, чьи данные помещаются в одну партицию, это чистые накладные расходы: 6 сетевых обращений и слияние вместо одного локального чтения. |
| **Выделенный кластер для топ-10 клиентов** | Рабочий вариант, применяемый в зрелых SaaS как отдельный тариф. Отклонён на текущем масштабе как преждевременный: даёт вторую инсталляцию со своей эксплуатацией ради 10 клиентов. Зафиксирован в backlog как вариант enterprise-тарифа. |

## Последствия

**Положительные**

- Стоимость на приложение — **581 ₽/мес** при выручке подписки на порядок выше;
  общий кластер делает unit-экономику продукта положительной.
- Запрос медианного клиента обслуживается **одним шардом** без сетевых обращений —
  отсюда `p95 ≤ 2 с` в НФТ.
- 1 024 бакета позволяют добавить седьмой шард, переселив ~14% бакетов,
  **без смены ключа шардирования** и без остановки записи.

**Отрицательные и что с ними делать**

- **«Шумный сосед» остаётся риском.** Полной изоляции нет: тяжёлый запрос крупного
  клиента конкурирует за CPU с остальными. Смягчение — профили ресурсов ClickHouse
  и перевод запросов дольше 10 с в асинхронный режим с отдельной очередью.
  Метрика «доля запросов, отклонённых по лимиту памяти» вынесена в раздел 8.
- **Ошибка в контроле доступа становится утечкой между клиентами** — самый тяжёлый
  класс инцидента для SaaS. Поэтому `app_id` берётся только из токена, а в CI
  есть отдельный тест, проверяющий, что ни один запрос Query API не читает `app_id`
  из тела. Дополнительно — row policy в ClickHouse как второй контур.
- **Переклассификация SMALL → LARGE — не мгновенная операция.** Приложение,
  выросшее за неделю, успеет накопить данные на одном шарде и получить медленные
  отчёты. Порог выставлен с запасом (12 с против бюджета 10 с — то есть класс
  меняется ещё до нарушения НФТ), а рост отслеживается предиктивным алертом
  по тренду, а не по факту превышения.
