# ADR-001. ClickHouse как основное аналитическое хранилище

| | |
|---|---|
| **Статус** | Принято |
| **Дата** | 2026-09-21 |
| **Контекст решения** | Раздел 4 «Хранение данных» |
| **Влияет на** | сайзинг (48% стоимости инфраструктуры), схему шардирования, формат запросов, RTO аналитики |

## Контекст

Система принимает **3 млрд событий в сутки** (104 тыс. событий/с на пике) и обслуживает
**20 аналитических запросов/с**. Соотношение записи к чтению — **3 400 : 1**.

Требования к хранилищу, вытекающие из НФТ:

- вставка 104 тыс. строк/с устойчиво, без деградации при параллельных запросах;
- `p95 ≤ 2 с` для стандартного отчёта на окне 30 дней и `p95 ≤ 10 с` для воронки
  или ретеншн-анализа на окне 90 дней;
- подсчёт уникальных пользователей по произвольным срезам (`uniq`), воронки
  с упорядоченными шагами, ретеншн-когорты;
- 90 дней детальных событий (5,4 ТБ на NVMe + 5,4 ТБ на объектном хранилище)
  и 3 года агрегатов;
- обновлений и удалений по одной строке в нормальном режиме нет — только
  массовое удаление по TTL и точечное удаление по GDPR-запросу.

## Решение

Основное аналитическое хранилище — **ClickHouse**: `ReplicatedReplacingMergeTree`
для детальных событий, `AggregatingMergeTree` через материализованные представления
для суточных агрегатов, многоуровневое хранение (`hot NVMe → cold S3`) через storage policy.

Конфигурация: **6 шардов × RF 2 = 12 узлов** по 16 vCPU / 64 ГБ / 2 ТБ NVMe.

## Рассмотренные альтернативы

| Вариант | Почему отклонён |
|---|---|
| **PostgreSQL + TimescaleDB** | Потолок вставки одной ноды — тысячи строк/с с учётом индексов, WAL и autovacuum. Для 104 тыс. строк/с потребовалось бы более 20 шардов только ради записи, а агрегаты по миллиардам строк всё равно считались бы минутами. Строчный движок принципиально не подходит для сканирования 5 из 40 колонок. |
| **Elasticsearch** | Годится для поиска и разбора логов, но `uniq` по миллиардам документов и воронки — не его сценарий; JVM-heap становится узким местом, а стоимость хранения в 3–4 раза выше ClickHouse при той же детализации. Для разбора сбоев (полнотекстовый поиск по стектрейсам) остаётся кандидатом, но заводить второе тяжёлое хранилище ради одного сценария дороже, чем жить с `ngrambf_v1`-индексом в ClickHouse. |
| **Apache Druid** | Закрывает те же сценарии и лучше в суб-секундных realtime-запросах. Отклонён по эксплуатационной цене: 5–6 типов узлов (broker, coordinator, historical, middle manager, overlord) против одного у ClickHouse, отдельный ZooKeeper и метабаза. Для команды курсового размера это несоразмерная сложность, а преимущество в latency не нужно: НФТ допускает 2 с. |
| **BigQuery / облачный DWH** | Снимает эксплуатацию, но цена считается за просканированные байты. При 20 RPS ad-hoc-запросов по 90-дневному окну счёт становится непредсказуемым и растёт от поведения клиентов, а не от объёма данных. Плюс требование резидентности данных (152-ФЗ) закрывает зарубежные управляемые сервисы. |
| **Data Lake (Parquet в S3 + Trino)** | Дёшево по хранению, но latency запроса — десятки секунд, что нарушает НФТ по дашбордам. Оставлен как слой для холодных данных: детальные партиции старше 30 дней лежат на S3-диске ClickHouse в том же формате. |

## Последствия

**Положительные**

- Сжатие 500 → 30 байт на событие (×17) за счёт `LowCardinality`, `Delta` + `ZSTD`
  на временных метках и колоночного хранения. Это прямой множитель стоимости: без него
  бюджет хранения вырос бы втрое.
- Материализованные представления считают агрегаты синхронно со вставкой — 95% дашбордных
  запросов вообще не трогают детальные данные и отвечают за десятки миллисекунд.
- Один тип узла, встроенная репликация, встроенное многоуровневое хранение.

**Отрицательные и что с ними делать**

- **Нет транзакций и полноценного UPDATE/DELETE.** GDPR-удаление реализуется
  через `ALTER TABLE ... DELETE` (мутация), которая переписывает части.
  Смягчение: удаления батчуются раз в сутки, срок исполнения запроса субъекта
  в НФТ заложен 30 дней, а не «немедленно».
- **`ReplacingMergeTree` схлопывает дубликаты только при слиянии**, то есть
  «когда-нибудь». Поэтому он не может быть единственным механизмом дедупликации —
  см. [ADR-003](ADR-003-at-least-once.md).
- **Дорогие JOIN.** Модель данных денормализована: атрибуты пользователя и устройства
  записываются в само событие, а не подтягиваются справочником. Цена — рост объёма,
  уже учтённый в 30 байтах на событие.
- **Слияния (merges) конкурируют за диск со вставкой.** Требуется следить за числом
  частей в партиции; при превышении ClickHouse начинает отклонять вставки.
  Вынесено в алерт (раздел 8, алерт №5) и в chaos-эксперимент №1.
