## 1. Компоненты

**API Gateway** — единая точка входа. Отвечает за аутентификацию токенов, rate limiting (защита от перегрузок), маршрутизацию запросов к нужному сервису. Разделяет upload-трафик контент-провайдеров и playback-трафик пользователей.

**Сервис транскодинга** — получает оригинальный файл из S3 и запускает параллельный пайплайн: FFmpeg перекодирует видео в несколько разрешений (240p, 480p, 720p, 1080p, 4K) и несколько битрейтов для каждого. Результат — набор сегментов (~2–10 сек) и манифест-файл HLS (.m3u8) или DASH (.mpd). Задачи ставятся через очередь (SQS / Kafka), чтобы пики загрузки не ронялиинфраструктуру.

**Стриминг-сервис** — реализует адаптивный битрейт (ABR): клиент раз в несколько секунд сообщает скорость соединения, сервис отдаёт манифест с URL сегментов подходящего качества. При деградации сети качество плавно снижается без прерывания воспроизведения.

**CDN (Content Delivery Network)** — набор edge-серверов по всему миру. Кэширует видеосегменты ближе к пользователю, снижая латентность и разгружая origin. Использует geo-роутинг: пользователь из Москвы получает сегменты с московского PoP, а не из датацентра в Вирджинии.

**Object Storage (S3)** — хранит оригинальный файл и все транскодированные версии. Отдаёт файлы CDN по pull-модели: CDN запрашивает сегмент у S3 при первом промахе кэша, затем хранит у себя.

**Сервис поиска** — индексирует метаданные (название, описание, теги, субтитры) в ElasticSearch. Обновляется событийно: при публикации видео отправляется событие в очередь, которую слушает сервис поиска.

**Сервис рекомендаций** — отдельная подсистема на базе ML-модели (коллаборативная фильтрация, embeddings). Использует историю просмотров, лайки и время удержания. Работает по расписанию (batch-пересчёт) и/или в реальном времени.

**Сервис аналитики** — собирает события (старт, пауза, перемотка, завершение, качество воспроизведения) через Kafka в колоночное хранилище (ClickHouse / BigQuery). Это отдельная подсистема от рекомендаций: аналитика отвечает за бизнес-метрики и дашборды, рекомендации — за персонализацию.

**Сервис пользователей** — хранит аккаунты, подписки, настройки. Является источником правды для авторизации.

**Session Cache (Redis)** — кэширует активные сессии и токены, чтобы каждый запрос не ходил в БД пользователей.

## 2. Потоки данных

### Сценарий 1: Загрузка нового видео провайдером

```
Контент-провайдер
  1 API Gateway (проверка токена, rate limit)
  2 Стриминг-сервис (получает URL для S3)
  3 S3 (прямая загрузка оригинала по URL)
  4 Сервис транскодинга (получает задачу на обработку)
      4.1 читает оригинал из S3
      4.2 параллельно создаёт 5 версий оригинала
      4.3 кладёт сегменты и манифест обратно в S3
  5 Сервис поиска индексирует метаданные
  6 API Gateway возвращает уведомление контент-провайдеру, что видео доступно
```

### Сценарий 2: Пользователь ищет видео

```
Клиент (вводит запрос)
  1 API Gateway проводит авторизацию через Redis
  2 Сервис поиска отправляет полнотекстовый запрос в ElasticSearch
      2.1 возвращает список ID + метаданные (название, превью, длина)
  3 API Gateway передает информацию клиенту (результаты с URL превью)
  4 CDN возвращает превью-картинки из кэша
```

### Сценарий 3: Пользователь запускает воспроизведение

```
Клиент (нажимает Play)
  1 API Gateway
  2 Стриминг-сервис
      2.1 проверяет права (активная подписка) через Сервис пользователей
      2.2 возвращает URL манифеста (HLS/DASH) на CDN
  3 Клиент запрашивает манифест у CDN
      3.1 отдаёт манифест из кэша, если манифеста нет, то запрашивает S3, потом кеширует и отдает
  4 Клиент выбирает качество (ABR: оценивает скорость соединения)
  5 Клиент загружает сегменты у ближайшего CDN
  6 клиент отправляет heartbeat в Сервис аналитики (раз в несколько секунд)
```

### Сценарий 4: Автоматическое снижение качества при деградации сети

```
Клиент (пропускная способность упала)
  1 ABR-алгоритм на клиенте пересчитывает целевой битрейт
  2 клиент переключается на другую полосу в манифесте (480p вместо 1080p)
  3 запрашивает сегменты низкого качества у CDN
  4 Сервис аналитики фиксирует снижение качества
  [Воспроизведение не прерывается — буфер покрывает переключение]
```

### Сценарий 5: Пользователь получает персональную подборку на главной странице

```
Клиент открывает главную страницу
  1 API Gateway → Сервис рекомендаций
      1.1 ML-модель смотрит историю просмотров пользователя
      1.2 возвращает список ID топ-20 видео
  2 Сервис рекомендаций в Metadata DB обогащает данные
  3 API Gateway передает информацию клиенту в ленту
  4 CDN возвращает превью-картинки из кэша
```

## 3. Проблемы и решения

**Стриминг-сервис + ABR** решает проблему "одно видео — разные сети". Без адаптивного битрейта пользователь с медленным соединением либо ждёт буферизации, либо получает низкое качество навсегда. ABR плавно подстраивает качество под реальную скорость в реальном времени.

**Сервис транскодинга** решает проблему хранения и доставки разных форматов. Хранить оригинал в одном формате и изменять его под каждого пользователя на лету — нецелесообразно. Вместо этого все варианты готовятся один раз при загрузке, нарезаются на сегменты и раскладываются в S3. Очередь задач позволяет масштабировать воркеры горизонтально в моменты пиковой загрузки.

**CDN** решает проблему латентности и стоимости трафика. Видео — тяжёлый трафик; если каждый байт идёт из единственного датацентра, пользователи из других регионов получают задержки, а origin перегружается. CDN амортизирует нагрузку: популярный контент кэшируется, большая часть запросов не доходят до S3.

**Object Storage (S3)** решает проблему надёжного хранения и одновременного доступа. Обычные файловые серверы не масштабируются до миллиардов файлов. S3 обеспечивает долговечность, версионирование и CDN-интеграцию.

**Сервис поиска** решает проблему полнотекстового поиска по метаданным. Реляционная БД плохо справляется с fuzzy-поиском, ранжированием по релевантности и фасетной фильтрацией. ElasticSearch решает всё это из коробки.

**Redis** решает проблему производительности аутентификации. Проверять токен через PostgreSQL на каждый запрос — узкое место при тысячах RPS.

**API Gateway** решает проблему разрозненного контроля доступа. Без шлюза каждый микросервис должен самостоятельно проверять токены и ограничивать нагрузку.
