# ДЗ 4. Сайзинг, стоимость и оптимизация — решение

> Условие: [../Задание.md](../Задание.md). Система — из [ДЗ 2](../../hw_02/solution/README.md),
> хранилища — из [ДЗ 3](../../hw_03/solution/README.md).

Система из ДЗ 2 — **сервис бронирования отелей** (аналог Booking): 8 сервисов, CQRS на чтении,
Saga на оформлении брони, polyglot persistence, Kafka + RabbitMQ.

Параметры из задания: **3 млн MAU, 300 тыс. DAU, 1 бронирование на пользователя в месяц,
пик ×5 в сезон отпусков.**

---

## Исходные данные и допущения

### Формулы

| Что считаем | Формула |
|---|---|
| Средний RPS | `RPS_avg = V_сут / 86 400` |
| Пиковый RPS | `RPS_peak = RPS_avg × k_сут × k_сезон` |
| Объём таблицы | `V = N_строк × S_строки × k_индексы × k_bloat` |
| Полоса | `Мбит/с = V_байт_сут × 8 / 86 400 / 10⁶` |
| Число инстансов | `N = ⌈(RPS_peak × t_cpu) / (vCPU_инстанс × U)⌉`, `U` — целевая утилизация 60% |
| Стоимость узла | `₽/мес = (vCPU × цена_vCPU + RAM × цена_RAM) × 730 ч × надбавка_managed + Диск × цена_диска` |

### Коэффициенты пиков

| Коэффициент | Значение | Обоснование |
|---|---|---|
| `k_сут` — внутрисуточный | **×2** | ~40% суточного трафика приходится на 4 вечерних часа. Средний час = 4,2% суток, пиковый ≈ 9% → ×2,1, округляю до 2 |
| `k_сезон` — сезонный | **×5** | из задания: пик в сезон отпусков |
| **`k_пик` итоговый** | **×10** | `k_сут × k_сезон` — пиковый час пикового дня сезона относительно среднегодового часа |
| `k_CM` — для channel manager | **×3** | B2B-поток слабо зависит от сезона: пик даёт ночная батчевая выгрузка тарифов |

Коэффициенты перемножаются: ×5 — это множитель к **суточному объёму**, внутри пикового дня
остаётся своя неравномерность.

### Профиль пользователя

Сессий на DAU в сутки — 1,3. Действий за сессию:

| Действие | За сессию | Пояснение |
|---|---|---|
| Автодополнение города | 6 | debounce при наборе |
| Поисковая выдача (SERP) | 5 | пользователь двигает даты и фильтры |
| Карточка отеля | 3 | из ~20 отелей выдачи открывают 3 |
| Календарь / проверка доступности | 4 | внутри карточки, при смене дат |
| Профиль, «мои брони» | 1 | |

Бронирований: `3 млн MAU × 1 ÷ 30 = 100 тыс./сут`. Холдов в 1,5 раза больше броней (часть
истекает по TTL), отмен — 15% от броней, платёжных операций — 2,1 на бронь
(authorize + capture + refund).

### Каталог и B2B-поток

Из ДЗ 3: **200 тыс. отелей × 8 типов номеров × 540 дней** горизонта продаж, 2 тарифных плана.
Channel manager обновляет в среднем **400 ячеек календаря на отель в сутки** (~5% календаря),
батчами по 100 строк на запрос.

## 1. Расчёт RPS

`V_сут = DAU × 1,3 сессии × действий_за_сессию` · `RPS_avg = V_сут / 86 400` · `RPS_peak = RPS_avg × 10`

| Эндпоинт | Тип | Объём/сут | RPS avg | **RPS peak** |
|---|---|---:|---:|---:|
| `GET /autocomplete` | чтение | 2 340 000 | 27,1 | **271** |
| `POST /graphql searchHotels` (SERP) | чтение | 1 950 000 | 22,6 | **226** |
| `GET /hotels/{id}` (карточка) | чтение | 1 170 000 | 13,5 | **135** |
| `CheckAvailability` (календарь) | чтение | 1 560 000 | 18,1 | **181** |
| `GET /users/me/bookings` | чтение | 390 000 | 4,5 | **45** |
| `CreateHold` | запись | 150 000 | 1,7 | **17** |
| `ReleaseHold` | запись | 50 000 | 0,6 | **6** |
| `POST /v1/bookings` | запись | 100 000 | 1,2 | **12** |
| `DELETE /v1/bookings/{id}` | запись | 15 000 | 0,2 | **2** |
| Payment authorize / capture / refund | запись | 210 000 | 2,4 | **24** |
| Channel manager (батчи по 100 строк) | запись | 800 000 | 9,3 | **28** (×3) |
| ↳ строк календаря в этих батчах | запись | 80 000 000 | 926 | **2 778** |
| **Итого через API Gateway** | | **8 735 000** | **101** | **946** |

**Read / Write = 14 : 1** на пользовательском API — количественное обоснование CQRS из ДЗ 2.
На уровне БД соотношение обратное: 2 778 строк/с от channel manager против 37 транзакций/с
от пользователей, то есть **98% записи в Inventory порождают отельеры, а не бронирующие.**

| Kafka | 9,5 млн событий/сут | **1 100 msg/s** |
| Внутренние gRPC-вызовы | fan-out 1,8 на внешний запрос | **1 703 RPS** |

## 2. Расчёт хранилища

`V = N_строк × S_строки × k`, где `k` — множитель индексов, bloat и репликации:
PostgreSQL ×1 (размер строки уже включает индексы и bloat), ScyllaDB ×4,5 (RF3 × 1,5 на compaction),
Elasticsearch ×6 (×2 индексы × RF2 × 1,5), Kafka ×3 (RF3).

только с ростом каталога; прошедшие месяцы отсекаются `DETACH PARTITION`. Линейно накапливаются
только брони, платежи и аналитика.

## 6. Оптимизация

Пять мер, ни одна не ухудшает пользовательские характеристики; первая их улучшает.

| # | Мера | Как работает и как считается экономия | Экономия, ₽/мес | Цена решения |
|---|---|---|---:|---|
| **1** | **AVIF/WebP + `srcset` + lazy-load** | превью 40 → 15 КБ, фото карточки 200 → 90 КБ; трафик CDN 105 → 47 ТБ, плюс половина origin egress | **63 682** (−8,5%) | нет: LCP падает, конверсия растёт. Нужен fallback в WebP/JPEG для старых клиентов |
| **2** | **CUD на 1 год для всех БД и 5 базовых нод k8s** | базовый слой работает 24/7 — платить on-demand за него нет причин; −30% на compute-часть (≈75% стоимости узла) | **127 382** (−17,0%) | обязательство на год; берём только на неснижаемую часть, пиковые ноды остаются on-demand |
| **3** | **HPA + Cluster Autoscaler под сезонный профиль, пиковые ноды — прерываемые ВМ** | 4 из 9 нод нужны 2 месяца в году и несут stateless-поды: `(9 − 5) × цена_узла × (1 − 2/12 × 0,5)` | **55 321** (−7,4%) | нужны корректные `PodDisruptionBudget` и прогрев; прерываемые ВМ только под stateless |
| **4** | **Tiered storage** | прошедшие партиции календаря (35% диска Inventory), сырые ответы PSP старше 90 дней (50% диска Payment), детальные события старше 12 мес → Object Storage вместо SSD | **30 645** (−4,1%) | доступ к архиву — минуты вместо миллисекунд; для аудита приемлемо |
| **5** | **Хит-рейт SERP-кэша 60% → 80%** | нормализация ключа (округление дат, канонический порядок фильтров) + прогрев топ-20 городов снимает нагрузку с ES: 3 × (8/32) → 3 × (4/16) | **26 171** (−3,5%) | +TTL-лаг на выдаче, уже принятый в ДЗ 3 как AP-компромисс |
| | **ИТОГО** | | **303 201** | **−40,5%** |

**749 485 → 446 285 ₽/мес, 5,4 млн ₽/год вместо 9,0 млн ₽.**
