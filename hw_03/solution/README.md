# ДЗ 3. Проектирование хранения данных — решение

> Условие: [../Задание.md](../Задание.md). Схемы — в [diagrams/](diagrams/).

Система из ДЗ 2 — **сервис бронирования отелей (аналог Booking)**: 8 сервисов, CQRS на чтении,
Saga на оформлении брони, Kafka как шина событий.

Расчеты были на 200 тыс. отелей по 8 типов номеров на 540 дней примерно 0,9 млрд строк календаря (~200 ГБ);
поиск **10 000 RPS**; обновления цен/квот от channel manager — пики **3 000 RPS на запись**;
создание брони ~200 RPS; ~30 млн броней в год (150 ГБ/год, retention 5 лет).
Овербукинг недопустим, устаревшая цена в выдаче — допустима.

## 1. Модель данных

ER-диаграмма: [diagrams/data-model.puml](diagrams/data-model.puml).
Внешних ключей между БД сервисов нет — связь только по идентификатору.

| Сервис                     | Сущности и ключевые поля                                                                                                                                                                                                                                            |
|----------------------------|---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| **User/Identity**          | users (user_id PK, email UQ, password_hash, locale); user_profile 1:1 (ФИО, loyalty_tier, preferences jsonb); session (токен -> user_id, TTL)                                                                                                                       |
| **Search** (read-model)    | hotel_doc — денормализованный документ отеля: name/description (анализируемые), geo_point, city, amenities[], rating, вложенные room_types и min_price_by_date, ссылки на фото. Не источник истины: собирается из событий HotelUpdated/RateChanged/InventoryChanged |
| **Inventory/Availability** | hotels; room_types (capacity, total_rooms); **availability_calendar — PK (hotel_id, room_type_id, date)**, поля total/booked/held/closed/version — самая большая и горячая таблица; holds (expires_at, status, idempotency_key UQ); outbox                          |
| **Booking**                | bookings (user_id, отель, даты, статус, total_price, hold_id, payment_id, idempotency_key UQ); booking_state_log — append-only лог переходов; saga_instance (шаг, компенсации, retry_count); outbox                                                                 |
| **Pricing**                | rate_calendar — цена на (hotel, rate_plan, date): base_price, min_stay, ограничения (объём как у календаря доступности, профиль — тяжёлая запись); rate_plans/promo — правила отмены и промокоды; quote — котировка с ограниченным сроком жизни                     |
| **Payment**                | payments (1:1 к брони, idempotency_key); payment_attempts (сырые запрос/ответ PSP); refunds; payment_tokens — **токен PSP, не карта** (PAN не хранится, PCI DSS)                                                                                                    |
| **Notification**           | delivery_log (кому/что/канал/когда/результат, retention 180 дней, читается по user_id); шаблоны в S3/конфиге; дедуп по event_id                                                                                                                                     |
| **Analytics/Audit**        | широкая таблица событий (поиск -> карточка -> холд -> оплата) и витрина bookings_by_hotel — read-model для партнёрского кабинета                                                                                                                                    |

## 2. Выбор БД

| Сервис | Что хранит и как читает | Выбранная БД | Почему |
|---|---|---|---|
| **User/Identity** | профили, credentials; точечно по user_id/email | **PostgreSQL** (+2 реплики) | малый объём, нужны целостность и транзакции |
| | сессии, токены; по ключу, ~5k RPS | **Redis** | эфемерные данные, TTL из коробки |
| **Search** | каталог; full-text, фасеты, geo, сортировка по цене, 10k RPS | **Elasticsearch** (6 шардов, RF=2) | ни одна OLTP-БД не даст морфологию + фасеты + гео на такой нагрузке; read-model безопасно перестраивается |
| | фото | **S3 + CDN** | бинарникам не место в БД |
| **Inventory/Availability** | календарь и холды; UPDATE ... WHERE по отелю и диапазону дат | **PostgreSQL, шардирован по hotel_id** | единственное место, где нужна **строгая** консистентность: овербукинг = прямые убытки. Eventual consistency неприемлема |
| **Booking** | брони, Saga, outbox; по booking_id и user_id | **PostgreSQL, шардирован по user_id** | ACID для переходов статуса + outbox в одной транзакции |
| **Pricing** | тарифный календарь; батчевая запись 3k RPS, чтение по узкому диапазону дат | **ScyllaDB/Cassandra** (RF=3, LOCAL_QUORUM) | ~1 млрд ячеек с постоянной перезаписью — профиль LSM, а не PostgreSQL с write amplification и вакуумом. Запросы всегда по ключу партиции. **Жертвуем** JOIN и транзакциями между отелями — они не нужны |
| | правила тарифов, промокоды | **PostgreSQL** | мегабайты данных, но нужна целостность |
| **Payment** | платежи, попытки, возвраты; сверка за период | **PostgreSQL** (отдельный кластер, PCI-контур) | деньги = ACID и полный аудит; 30 млн строк/год живут на одной ноде с партиционированием — **не шардируем** |
| **Notification** | лог доставки; по user_id за последние дни | **ScyllaDB/Cassandra** | миллиарды строк, ~100% запись, native TTL и дешёвое удаление старого |
| | дедуп событий (SETNX по event_id) | **Redis** | защита от повторной отправки при at-least-once |
| **API Gateway** | rate-limit, ключи идемпотентности; INCR ~15k RPS | **Redis** | атомарные счётчики с TTL |
| **Analytics/Audit** | события, отчёты партнёрам; агрегаты по миллиардам строк | **ClickHouse** | такие GROUP BY в OLTP-БД убивают прод |

**6 семейств:** реляционное, поисковое, wide-column, key-value, колоночное, объектное.
PostgreSQL остаётся там, где корректность важнее масштаба (деньги, брони, инвентарь) — но это
разные кластеры, а не одна база «на всё». NewSQL (CockroachDB) не берём: распределённый консенсус
на каждый commit добавляет латентность на самом критичном пути; оставляем как план Б.
Семейств шесть, а не десять, потому что каждое хранилище — это дежурства и бэкапы:
ScyllaDB переиспользуют два сервиса, Redis — четыре.

## 3. Шардирование

Схема: [diagrams/sharding.puml](diagrams/sharding.puml).

Шардирование нужно для Inventory (0,9 млрд строк, 3k RPS записи; реплики не помогают, узкое место — запись).
для Booking — пограничный случай, тк для RPS хватило бы одной ноды, но со временем объём не влезет,
поэтому схему закладываем сразу, чтобы не мигрировать «на живом». Payment, User, правила Pricing —
**не шардируем**, хватает партиционирования по месяцам и реплик. ES, Scylla, ClickHouse шардирует движок.

### 3.1. Inventory — ключ hotel_id

| Кандидат            | Равномерность                    | Локальность запросов                                                                                        | Вывод                                              |
|---------------------|----------------------------------|-------------------------------------------------------------------------------------------------------------|----------------------------------------------------|
| city_id             | плохая (Москва против райцентра) | высокая                                                                                                     | нет, hotspot + сезонные пики                       |
| room_type_id        | отличная                         | плохая: карточка отеля = запрос ко всем шардам, холд на два номера одного отеля = распределённая транзакция | нет                                                |
| date (range)        | —                                | ужасная                                                                                                     | нет, весь трафик в «ближайшие 90 дней» = один шард |
| **hotel_id (hash)** | высокая                          | высокая: весь календарь отеля в одном шарде                                                                 | да                                                 |

Почему: единица бизнес-транзакции — «холд на номера конкретного отеля на конкретные даты».
Ключ делает такую транзакцию **локальной для одного шарда**, то есть обычной ACID-транзакцией
PostgreSQL. Массовых запросов «по всем отелям» у Inventory нет: их обслуживает ES (CQRS).

Стратегия — hash + логические бакеты.

Не hash % N по числу нод — при добавлении девятой переезжает почти всё. Не consistent hashing —
1024 бакета дают ту же плавность, но проще и позволяют вручную переселить горячий бакет.

| Параметр       | Значение                                                                                                                                             |
|----------------|------------------------------------------------------------------------------------------------------------------------------------------------------|
| Старт          | 8 шардов × (primary + 2 реплики), по 128 бакетов; ~25 ГБ на шард                                                                                     |
| Рост           | до 1024 шардов без смены ключа                                                                                                                       |
| Внутри шарда   | availability_calendar секционирована PARTITION BY RANGE (date) помесячно, прошедшие месяцы — DETACH + архив                                          |
| Ребалансировка | целыми бакетами: логическая репликация -> пауза записи по бакету (сотни мс) -> переключение карты. 9-я нода = переезд ~11% данных без общего простоя |


### 3.2. Booking — ключ user_id

booking_id (hash) дал бы идеальную равномерность, но «мои брони» превратились бы в scatter-gather
по всем шардам при каждом входе в ЛК; hotel_id — hotspot на крупных сетях. user_id держит историю,
брони и лояльность одного пользователя в одном шарде. Старт — 2 шарда по 512 бакетов.

**Риски.** Корпоративные аккаунты и тревел-агентства — единственный источник перекоса; выносим их
в directory-override (user_id -> выделенный шард, ~сотня записей). Запрос «все брони отеля» —
cross-shard по определению, решается витриной bookings_by_hotel в ClickHouse из Kafka.
Saga и outbox лежат в шарде брони, атомарность сохранена.

## 4. Кэширование

| Что кэшируем                    | Уровень                    | Стратегия     | TTL                           | Инвалидация              | Зачем                                                                                     |
|---------------------------------|----------------------------|---------------|-------------------------------|--------------------------|-------------------------------------------------------------------------------------------|
| Фото, статика                   | CDN                        | write-around  | 30 дней                       | версия в URL             | 90% байт не доходит до бэкенда                                                            |
| Карточка отеля                  | Caffeine (L1) + Redis (L2) | cache-aside   | 5 с / **1 час**               | событие HotelUpdated     | меняется раз в недели, читается 1 500 RPS                                                 |
| Результаты поиска (SERP)        | Redis                      | cache-aside   | **60 с**                      | по TTL                   | топ-10% запросов дают >60% трафика; ключ — нормализованный city+dates+guests+фильтры+page |
| Справочники (города, валюты)    | Caffeine                   | read-through  | **1 час**                     | событие + рестарт пода   | читаются в каждом запросе                                                                 |
| Профиль пользователя            | Redis                      | cache-aside   | **15 мин**                    | событие UserUpdated      | многократное чтение при оформлении                                                        |
| Сессии, JWT-denylist            | Redis                      | write-through | = сроку токена                | сброс при logout         | Redis здесь источник истины, а не кэш                                                     |
| Котировка цены                  | Redis                      | write-through | **5 мин** = сроку предложения | по TTL                   | цена не должна «прыгать» между шагами                                                     |
| Признак «есть свободные номера» | Redis                      | cache-aside   | **30 с**                      | событие InventoryChanged | снимает ~90% чтений с шардов Inventory                                                    |

**Осознанно не кэшируем:**

- **точный остаток номеров перед холдом** — кэшированный счётчик = овербукинг. Кэш отвечает только
  на вопрос «показывать ли отель в выдаче», решение о холде принимает транзакция в PostgreSQL;
  расхождение обрабатывается как 409 -> «номер только что забронировали»;
- **платежи, состояние Saga, персональные брони** — read/write ratio ≈ 1, свежесть критична, PCI;
- **долгий хвост поисковых запросов** — hit rate единицы процентов, только вытеснял бы горячие ключи.

**Проблемы:** 
отказ Redis — circuit breaker с походом
в БД и ужесточением rate limit; вытеснение — allkeys-lru, при этом кэш и состояние (сессии,
идемпотентность, noeviction + AOF) разнесены по разным инстансам.

## 5. Очереди

| Где | Брокер | Почему |
|---|---|---|
| Доменные события: BookingCreated/Confirmed/Cancelled, PaymentAuthorized/Failed, InventoryHeld/Released, RateChanged | **Kafka** | один факт нужен нескольким независимым потребителям (Search, Notification, Analytics, продолжение Saga); нужен retention и **replay** — перестроить индекс ES, проиграв топик заново |
| Реиндексация read-model поиска (CQRS) | **Kafka** | пики от channel manager (3k RPS) буферизуются, ES не обязан держать пик синхронно |
| Поток в аналитику и аудит | **Kafka -> ClickHouse** | тот же поток, ещё один потребитель, без нагрузки на OLTP |
| Публикация событий из сервисов | **Transactional Outbox + Debezium CDC** | событие не потеряется и не уйдёт без коммита бизнес-данных |
| Отправка email/SMS/push | **RabbitMQ** | это **задача, а не факт**: per-message ack, индивидуальные ретраи с backoff, DLQ, приоритеты. В Kafka застрявшее сообщение блокирует партицию, а retry-топики — ручная реализация того, что в RabbitMQ есть из коробки |
| Напоминание «заезд через 24 ч», истечение холда | **RabbitMQ delayed exchange** + таблица-планировщик | отложенная доставка не решается брокером логов; для холдов дополнительно sweeper по expires_at — брокер может потерять таймер, БД не потеряет |

Гарантии: всюду **at-least-once**, exactly-once не закладываем (дорог и иллюзорен на границе с PSP) —
вместо него идемпотентные потребители с дедупом по event_id. Ключ партиции Kafka: booking_id
для брони и платежей (порядок переходов статуса), hotel_id для инвентаря и цен. На каждом
консьюмере — DLQ и алерт; схемы событий в Schema Registry с проверкой совместимости.

## 6. CAP trade-offs

Выбор делается не для системы целиком, а для каждого хранилища — в этом смысл polyglot persistence.

| Компонент | CAP | Поведение при partition | Цена |
|---|---|---|---|
| **Inventory** (PostgreSQL) | **CP** | при потере кворума отказываем в записи (503/409 вместо холда), failover через Patroni+etcd | 15–30 с недоступности записи по одному шарду (1/8 отелей). Дешевле, чем овербукинг: продать номер дважды = компенсация гостю + репутация |
| **Booking** (PostgreSQL) | **CP** | synchronous_commit = remote_apply на синхронную реплику | +2–5 мс на commit; потеря подтверждённой брони недопустима |
| **Payment** (PostgreSQL) | **CP**, строже всех | отказ в проведении платежа | двойное списание дороже любого простоя |
| **Search** (Elasticsearch) | **AP** | отдаём выдачу из доступных нод, даже отставшую | лаг 1–5 с, возможна устаревшая цена. Компенсируется продуктово: цена и доступность перепроверяются на шаге оформления. Пустая выдача хуже слегка устаревшей |
| **Pricing calendar** (ScyllaDB) | **AP**, tunable | RF=3, LOCAL_QUORUM: переживаем потерю одной ноды из трёх | цена отстаёт на секунды, финальная фиксируется котировкой |
| **Notification** | **AP** | копим и отправляем позже | at-least-once -> возможен дубль письма; дубль приемлем, неотправленное подтверждение — нет |
| **Redis-кэш** | **AP** | деградация в БД | stale в пределах TTL; для сессий — отдельный кластер с AOF |
| **Kafka** | **CP** по партиции | acks=all, min.insync.replicas=2: продюсер получает ошибку вместо «тихой» потери | продюсер обязан ретраить/писать в outbox |


Система остаётся полезной, будучи частично CP, за счёт CQRS: при недоступности шарда Inventory
поиск, карточки и история броней продолжают работать из AP-хранилищ — деградирует только оформление
брони по части отелей. Строгая консистентность локализована в минимальном контуре
(hotel_id, room_type_id, date) внутри одного шарда — поэтому её и удаётся себе позволить.
