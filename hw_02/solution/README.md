# ДЗ 2. Проектирование взаимодействия сервисов

## Выбранная система

**Сервис бронирования отелей (аналог Booking).**

Ключевые сложности:

- **Ресурс и овербукинг.** Один и тот же номер на одни даты нельзя продать дважды.
  Нужна строгая консистентность на уровне единицы инвентаря и механизм временных
  холдов.
- **Оплата.** Работа с деньгами и бронью должна проходить через распределённую транзакцию.
  Нужна Saga с компенсациями и идемпотентность.
- **Отмены и возвраты.** Освобождение ресурса брони, законный возврат средств - это
  асинхронные события с гарантией доставки.
- **Разная нагрузка на чтение и запись.** Поиск (read-heavy, тысячи RPS) и запись брони
  (строгая консистентность, меньше RPS) имеют разные требования, поэтому нужно использовать CQRS.

## 1. Декомпозиция

Определено 8 сервисов. Границы проведены по бизнес-возможностям и по разнице в требованиях к консистентности/нагрузке.

| # | Сервис                               | Ответственность                                                                                   | Почему отдельный                                                                                           |
|---|--------------------------------------|---------------------------------------------------------------------------------------------------|------------------------------------------------------------------------------------------------------------|
| 1 | **API Gateway**                      | Единая точка входа, аутентификация, rate limit, роутинг, агрегация ответов под устройство клиента | Клиентам нужна агрегация из нескольких сервисов; не нужно допустить протекания внутренней топологии наружу |
| 2 | **Search Service**                   | Поиск и фильтрация объектов размещения, каталог, автодополнение. Read-model поверх Elasticsearch  | Read-heavy, полнотекстовый поиск, отдельное масштабирование и хранилище (CQRS-read)                        |
| 3 | **Inventory / Availability Service** | Доступность номеров, календарь, временные холды, защита от овербукинга                            | Необходима строгая консистентность; критично изолировать от read-нагрузки                                  |
| 4 | **Booking Service**                  | Жизненный цикл брони (созданиеб подтверждение, отмена), оркестрация Saga                          | Владелец бизнес-процесса, оркестратор; координирует цену и оплату                                          |
| 5 | **Pricing Service**                  | Расчёт итоговой цены, налоги/сборы                                                                | Часто меняющиеся правила ценообразования                                                                   |
| 6 | **Payment Service**                  | Авторизация/списание, возвраты, идемпотентность платежей                                          | Требования PCI DSS, изоляция чувствительных данных                                                         |
| 7 | **User / Identity Service**          | Профили, аутентификация, история бронирований пользователя                                        | Переиспользуется всеми; отдельный контур безопасности                                                      |
| 8 | **Notification Service**             | Email/SMS/push: подтверждения, напоминания, отмены                                                | Потребитель событий; не должен блокировать основной поток                                                  |

## 2. Протоколы

Принцип - gRPC внутри, REST/GraphQL наружу, асинхронно через брокер, прогресс брони — SSE.

| Взаимодейстиве                      | Протокол           | Обоснование                                                                                                                                    |
|-------------------------------------|--------------------|------------------------------------------------------------------------------------------------------------------------------------------------|
| Клиент - API Gateway (чтение)       | **GraphQL**        | Web и mobile тянут разный набор полей (карточка отеля, цена, отзывы). GraphQL убирает over/under-fetching и даёт один запрос вместо нескольких |
| Клиент - API Gateway (команды)      | **REST**           | Создание/отмена брони — простые идемпотентные HTTP-команды, легко кэшировать                                                                   |
| API Gateway - Клиент (статус брони) | **SSE**            | Односторонний поток server - client: «холд создан -> оплата -> подтверждено». Можно WebSocket, не нужен обратный канал                         |
| API Gateway - внутренние сервисы    | **gRPC**           | Внутренний трафик: low latency, строгий контракт (.proto), генерация клиентов, HTTP/2-мультиплексирование                                      |
| Booking - Inventory                 | **gRPC**           | Критичный синхронный путь (hold номера), нужен строгий контракт и минимальная задержка                                                         |
| Booking - Pricing / Payment         | **gRPC**           | Синхронные команды в рамках паттерна Saga; строгий контракт, low latency                                                                       |
| Payment - PSP                       | **REST + webhook** | Интеграция по стандарту эквайера; результат приходит асинхронно вебхуком                                                                       |
| Все сервисы - Kafka                 | **events (Kafka)** | Развязка во времени, буфер пиков, гарантии доставки, несколько независимых потребителей одного факта                                           |
| Search Service - Elasticsearch      | **query**          | Нативный протокол хранилища read-model                                                                                                         |

## 4. API-контракты

### 4.1. Search API (GraphQL)

Чтение под нужды клиента. Версионирование — эволюцией схемы (добавление полей обратно
совместимо, удаление — через `@deprecated`).

```graphql
type Query {
  searchHotels(
    city: String!
    checkIn: Date!
    checkOut: Date!
    guests: Int! = 2
    page: Int = 0
  ): HotelSearchResult!
}

type HotelSearchResult {
  total: Int!
  items: [Hotel!]!
}

type Hotel {
  id: ID!
  name: String!
  rating: Float
  minPrice: Money!
  photos: [String!]!
  rooms: [RoomOffer!]!
}

type RoomOffer {
  roomTypeId: ID!
  title: String!
  price: Money!
  refundable: Boolean!
  freeCancellationUntil: DateTime @deprecated(reason: "use cancellationPolicy")
}
```

### 4.2. Availability / Hold API (gRPC)

Строгий контракт на критичном пути. Идемпотентность холда через `idempotency_key`.

```protobuf
syntax = "proto3";
package inventory.v1;

service InventoryService {
  rpc CheckAvailability (CheckAvailabilityRequest) returns (CheckAvailabilityResponse);
  rpc CreateHold        (CreateHoldRequest)        returns (Hold);
  rpc ReleaseHold       (ReleaseHoldRequest)       returns (ReleaseHoldResponse);
}

message CreateHoldRequest {
  string room_type_id    = 1;
  string check_in        = 2;  // ISO-8601 date
  string check_out       = 3;
  int32  rooms           = 4;
  string idempotency_key = 5;  // повтор запроса не создаёт второй холд
  int32  ttl_seconds     = 6;  // авто-освобождение, напр. 900
}

message Hold {
  string hold_id     = 1;
  string status      = 2;  // HELD | EXPIRED | RELEASED | COMMITTED
  string expires_at  = 3;
}
```

### 4.3. Booking API (REST)

Команда создания брони. **Idempotency-Key** в заголовке защищает от двойного создания
при ретраях. Версия — в URL (`/v1/`).

```http
POST /v1/bookings
Idempotency-Key: 5f3c...-a91
Content-Type: application/json

{
  "hotelId": "h_123",
  "roomTypeId": "rt_5",
  "checkIn": "2026-08-01",
  "checkOut": "2026-08-04",
  "guests": 2,
  "paymentMethodId": "pm_88"
}
```

```http
201 Created
{
  "bookingId": "bk_9001",
  "status": "PENDING_PAYMENT",
  "totalPrice": { "amount": 27000, "currency": "RUB" },
  "holdExpiresAt": "2026-07-01T12:15:00Z"
}
```

Ошибки: `409 Conflict` — номер уже недоступен (холд не удался); `402` — оплата отклонена;
`422` — некорректные даты. Отмена — `DELETE /v1/bookings/{id}` (тоже идемпотентна).

### 4.4. Payment API (gRPC)

Двухшаговая оплата под Saga, идемпотентность и возвраты.

```protobuf
service PaymentService {
  rpc Authorize (AuthorizeRequest) returns (Payment);  // холд средств
  rpc Capture   (CaptureRequest)   returns (Payment);  // фактическое списание
  rpc Refund    (RefundRequest)    returns (Refund);   // компенсация Saga
}

message AuthorizeRequest {
  string booking_id       = 1;
  Money  amount           = 2;
  string payment_method_id= 3;
  string idempotency_key  = 4;
}
```

## 5. Асинхронность

Асинхронное взаимодействие (Kafka) применяется там, где вызывающему **не нужен ответ
синхронно** и важна устойчивость к пикам:

- **Нотификации.** После подтверждения брони Booking публикует событие `BookingConfirmed`;
  Notification Service шлёт письмо. Отправка письма не должна влиять оформление брони.
- **Реиндексация поиска (CQRS).** Изменения цен/доступности (`RateChanged`, `InventoryHeld`)
  прилетают событиями в Search и обновляют read-model в Elasticsearch. Поиск не ходит в
  Inventory синхронно — он читает свою реплику.
- **Результат оплаты.** Эквайер отвечает вебхуком асинхронно; Payment публикует событие
  `PaymentAuthorized`/`PaymentFailed`, Saga двигается дальше.
- **Аналитика/аудит.** Любой сервис-подписчик читает события, не влияя на основной поток.

Надёжность публикации обеспечивает **Transactional Outbox**: событие пишется в БД в одной
транзакции с бизнес-данными, затем публекуется в Kafka

## 6. Паттерны

| Паттерн                               | Где                                                                                                                   | Зачем                                                                                                           |
|---------------------------------------|-----------------------------------------------------------------------------------------------------------------------|-----------------------------------------------------------------------------------------------------------------|
| **Saga (оркестрация)**                | Booking Service координирует шаги: `CreateHold - Authorize - Confirm`; при сбое — компенсации `ReleaseHold`, `Refund` | Распределённая транзакция бронировния и оплаты; явный оркестратор проще отлаживать, чем хореографию             |
| **CQRS**                              | Запись в Inventory/Booking для строгой консистентности ; чтение для поиска в Elasticsearch (обновляется событиями)    | Разные требования: поиск — тысячи RPS и сложные фильтры, запись — консистентность. Разделяем модели и хранилища |
| **Transactional Outbox**              | Booking / Payment / Inventory при публикации событий                                                                  | Атомарность при изменении данных и публикации события, без потери событий при падении                           |
